## 4. Phase C3 — replace N102 numeric aliasing with an event-object identity test

**Diagnosed limitation (not a claim that an actual leak occurred):** Windows inheritance documentation states an inherited handle refers to the **same object**, but a child can independently obtain a handle of the **same integer value** to a different object. Current N102_01 and `n102_probe_handle_v1` use `GetHandleInformation(value)`; the WO-108 and WO-110 failures showed numeric matches in the child without proving object identity. Do not solve this by ignoring `live=true`, removing the control, altering two-handle inheritance, adding a retry in the test or weakening N102 to an always-green check.

**Corrected identity method:** Parent creates one *real*, anonymous manual-reset `CreateEventW` object with `bInheritHandle=TRUE`, explicitly excluded from the production `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Parent also creates a non-inheritable event control; both start **nonsignaled** and remain owned/alive until after the child is fully reaped. Child in a **new closed N102-only reserved probe mode** attempts `SetEvent` on the two transmitted numeric candidate values after it proves its own confinement. Parent then uses `WaitForSingleObject(original_parent_event_handle, 0)`, requiring `WAIT_TIMEOUT`, on **both original parent objects**. An independently reused number cannot signal the original parent event; a genuinely inherited event handle with `EVENT_MODIFY_STATE` would signal the **same kernel object** and cause a failing parent assertion. Report only bounded booleans, a verified child PID, and the local signal-API witness — no raw handle values. Both child and parent must prove `SetEvent` and the event-state observation work with **separate positive controls**; a failed or unexecuted attempt, invalid wait or ambiguous result fails closed.

Microsoft normative API documentation (reviewed 2026-11-14):
- Handle inheritance and same-object semantics: `https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance`
- Only explicit allowlisted handles should be inherited: `https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes`
- `SetEvent` signals a kernel event: `https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setevent`
- `WaitForSingleObject(…, 0)`, `WAIT_TIMEOUT`, `WAIT_OBJECT_0`, `WAIT_FAILED`: `https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject`
