### I. Foundation, precedence and scope

1. One Solo Installation contains **exactly one Entity**, whose published graph is `Entity → Facet (1+) → Site (1+ per Facet) → Page (1+ per Site) → localized representation (1+ per published Page)`. There is no Spoke, Spoke Hub, separate publishing entity, multi-Entity tenant or geographic hierarchy.
2. Every published child has one direct parent; a draft or unfinished declaration is allowed only *outside* the authoritative published graph. Published includes **unlisted** representations. Presence of a file does not create a published Page, representation, route or asset inventory entry.
3. R00.D specifies *physical* content/publication declarations. It implements, and does not revise except where specifically Owner-amended, R00.A's identity/source rules, R00.B's routes/locales/visibility rules and R00.C's governed additive properties/location/graphics rules.
4. The only publication authority is the versioned, directly authored JSON manifest. All JSON, Markdown, metadata, assets, modules, derived registries and generated output are subordinate to that authority.
5. The D03 Owner amendment replaces **single declared physical file** with **one explicit source-selection declaration allowing two known candidates and exactly one effective resolved authored source**. This changes no EFS/publication membership. Older Charter wording asserting a single source *reference* must be reconciled, not left contradictory.
6. Mandatory strict Hexagonal Architecture: EFS identity, route, property, exposure, publication and module contract rules are domain/application policies; filesystem, parsing, rendering, provider SDK, public HTTP transport and asset processing are replaceable adapters behind explicit ports. Dependencies point inward only. No implementation stack or deployment provider is selected by R00.D.
7. Security, accessibility, privacy, portability, publication integrity and truthful diagnostics are binding constraints, not optional rendering preferences. Advanced JSON modules must not create capabilities expressly excluded by the accepted Product Definition (notably advanced contact-form builders or CRM workflows).

### D02 — Nested EFS declarations, identities and direct parentage

**ACCEPTED:** Physical manifest uses one nested ownership tree: Entity contains Facets; each Facet Sites; each Site Pages; each Page localized representation declarations. Facet IDs are unique within Entity, Site IDs within their own Facet, Page IDs within their own Site; identical `main` or `home` at other levels/scopes are legitimate. Reparenting, ID change, deletion require explicit later-approved migrations and reference integrity; physical movement of a declaration is not an implicit migration. A usable starter Installation has an Owner-supplied Entity ID, `main` Facet, `main` Site, `home` Page, and real content in an explicitly chosen supported full locale; defaults are editable initial seeds, not reserved IDs.

### D03 — Two declared candidates, JSON-first, one effective source (AMENDED)

**ACCEPTED, final Owner amendment superseding the original D03 single-file declaration:** Each published representation declares a *single authoritative source-selection contract* with at most two **explicitly named** candidate locators, one JSON and one Markdown. The author must declare at least one candidate; declaring both permits automatic Markdown-to-JSON upgrade without editing the manifest. Never discover candidate paths from file names, route, Page ID, locale, directory scans, globbing, file order, extension guessing or a neighbouring representation. The source-selection algorithm is:

1. Validate declared candidate locator syntax, namespaces and candidate ownership/uniqueness. Resolve the explicitly designated JSON locator if supplied. Distinguish genuine absence from access denial, invalid locator, unsafe redirection/symlink, unreadability, ambiguity or I/O error; those errors **block publication**, not fallback.
2. If the JSON candidate exists, it is *the only selected source*. Parse and validate it; invalid JSON, unsupported schema, invalid module, insecure content or wrong file type blocks the entire proposed publication. **Never fall back to Markdown because existing JSON is invalid.**
3. If JSON is genuinely absent (or no JSON candidate is declared), resolve the explicitly designated Markdown candidate. If present and valid, it is the sole selected source; if absent, unsafe or invalid, publication fails.
4. When both exist, JSON wins and Markdown is unselected. Their bodies are never merged and the file iteration order has no influence. Unselected Markdown's content need not be parsed, but its authored candidate locator and ownership are still validated.
5. Duplicate or overlapping claims to the same canonical authored source across distinct published representations, **including a candidate not currently present**, are refused. Multiple spellings or indirections to the same source may not evade the check. Intended source sharing or generated source content requires its own later Owner-approved contract.
6. A file not claimed by the manifest cannot create a Page or representation. An incomplete draft may remain outside published source authority; publishing it requires explicit graph admission and full validation. Generated outputs and public assets are not authored content authorities.
7. Selected-source identity and a safe diagnostic explaining the JSON-first choice are available for authoring/verification. Changing a file path or switching Markdown to JSON does not mint a new EFS identity or alter routing/visibility/property authority.

**Test truth table:** `(JSON absent, MD valid)→MD`; `(JSON valid, MD absent)→JSON`; `(JSON valid, MD valid)→JSON`; `(JSON invalid present, MD valid)→REFUSE`; `(both absent)→REFUSE`; `(JSON permission denied, MD valid)→REFUSE`; `(two representations reserve same candidate)→REFUSE`.

**SPECIFICATION GATE:** Final keys for `sourceCandidates` and candidate locator syntax, whether omission versus explicit null permitted, existence atomicity/TOCTOU policy, hash/canonical alias detection and race-safe publication snapshot handling remain to be specified. Do not force hash pins (rejected extra workflow), permit implicit scan, or treat `null` as an unreviewed wildcard.

Registry has stable built-in and governed custom definitions: value type, allowed EFS levels, effective cardinality, equality/uniqueness, maximum public exposure, permitted special operations and validation. Unknown/conflicting definitions refuse publication. A property wholly absent at a node implicitly inherits its direct parent result. If authored, it has **two independent elements** `inheritance: inherit | suppress` and `currentContext: none | zero-or-more typed local values`; `none` applies only to local contribution. `inherit` carries ancestor effective values, ordered inherited-first then local; `suppress` clears inherited input but permits local additions; root inherited input is empty. A registered max applies to **effective** values; a singular inherited plus local selection violates cardinality unless valid suppression/special operation, never implicit nearest-value-wins. No silent deduplication, merge or order precedence. Inheritance follows immediate EFS ancestry only; siblings, locale, location and routes confer no ancestry. Resolved values preserve per-value origin, suppress/inclusion decisions and permitted field provenance. Each value has explicit exposure within registered maximum. The domain's validated public projection is the **only** input to public HTML, scripts, JSON, metadata, feeds and presentation modules; omission of internal values never causes an arbitrary public ancestor to replace them. Public repo assets/data cannot be considered secret merely because `internal` is used. Every invalid or unlisted property still blocks complete publication.

**SPECIFICATION GATE:** Full physical registry catalog and value envelopes, exact `none` encoding, enum spelling and cross-type uniqueness/equality and exposure-classification set must be finalized; example key `topics` is not an automatically accepted built-in.

### D09 — Location structured facts and identified extension

**ACCEPTED:** `location` is an optional registered property at every EFS level with zero or more structured facts; no mandatory premises, country, city, postal address or coordinates. Distinct types can represent world region, country, state/province, locality, district, named place/area, postal fields, explicit coordinates, association versus premises, and governed typed custom metadata. A fact has stable authored `factId`, original qualified EFS owner, type, registered fields and whole-record exposure. A new independent fact uses explicit `add` operation; it is not implicitly merged with inherited fact. An `extend` operation identifies **exactly one accessible inherited record** by original fully qualified identity and supplies bounded explicit field additions/replacements. It updates that fact **in place** without appending a duplicate or changing its ID/order, preserves original provenance for untouched fields, and records local field provenance for modified fields. Missing, cross-branch, ambiguous, suppressed or circular targets, conflicting same-node extensions or invalid fields are refused. Suppression excludes inherited facts, so extending a suppressed record is invalid. An internal inherited fact or internal inherited field cannot be silently promoted to public; whole-record exposure applies and no implicit per-field publication policy exists. No implicit primary when several facts exist; any one-record consumer requires explicit governed selection. Geographic correctness is authored responsibility; Solo validates types and safe serialization but neither geocodes nor claims external verification. Neither URL, Site ID, hostname, language, region tag nor coordinates can infer or modify locations or routes. Location never forms a mandatory EFS tier.

**SPECIFICATION GATE:** Full field/type catalog, fact ID grammar, typed coordinate profile, qualified target encoding, operation patch grammar, uniqueness of whole-record origin and field provenance/visibility rules require finalized schemas; sample key names `factId`, `operation`, `target`, `set` remain proposed until defined as canonical syntax.

### D10 — Cascading registered graphics and typed asset sources

**ACCEPTED:** Graphic selections are D08 properties with the same `inheritance` and `currentContext` semantics. Registered roles govern allowed asset classes, EFS levels, contexts, cardinality and exposure. Candidate initial roles include logo, favicon, banner, background and socialPreview; their final exact names, formats and cardinalities are not yet automatically selected. A singular effective role accumulating inherited+local entries fails instead of silently overriding; `suppress` may remove inherited and then accept valid local selection. Two explicit typed asset-source namespaces: one Entity-owned authored source and one read-only shared generic platform public library available throughout the Installation, without becoming an EFS node or alternate Entity/publisher. Namespace ownership must be declared, never inferred from public URL, filepath, locale or output. Any unregistered/unsafe/ambiguous/wrong-class/missing declared asset fails; zero roles initially approve automatic generic fallback. Explicitly selecting a generic asset is an authored value, not fallback. Invalid private/suppressed values cannot be resurrected by fallback. Source assets authoritative; transformed/optimized outputs derived. Advanced JSON modules can accept **direct typed media asset references** for watermarks, backgrounds, galleries, carousels and layered heroes without making every media item a cascading graphic property. Module inputs remain validated and no arbitrary file/remote fetch is allowed.

**SPECIFICATION GATE:** Registry role identifiers, source reference grammar, MIME/media allowlists, asset format handling (including potentially active SVG), maximum bytes/dimensions, transformation lifecycle and generic library version compatibility are not yet finalized by accepting D10 Option A.

### D11 — Safe relative locators, content/asset/link separation

**ACCEPTED:** Source locators, typed asset references and public links are different semantic contracts. Publication content sources resolve only within their permitted logical authored-content namespace; Entity-owned assets and read-only platform generic assets have separate explicit namespaces; drafts and derived output are not publication source authority. Logical namespace ≠ new EFS owner. Prefer portable relative `/`-separated source locators. Reject absolute paths, drive letters, UNC, home expansion, empty/dot/dotdot segments, backslash ambiguity, control and null bytes, URL-escaped path decoding ambiguities, unsafe queries/fragments in filesystem locators, unsupported indirection and symlink traversal. Verify **resolved containment** within assigned boundary; string prefix comparison alone is insufficient. Validate both D03 candidate locator declarations and cross-representation source ownership even if a candidate is absent. For JSON-first selection, only genuine preferred JSON absence permits Markdown; unsafe or unreadable preferred file is refusal. Never accept direct paths into secrets, configuration, drafts, implementation code or generated assets as source authority. Public URL generation uses D07 canonical route/authorized action and base prefix exactly once, not a storage path. Markdown stays ordinary syntax: `[text](relative-reference)`, `![alt](relative-media)` and recognized external HTTP(S), safe `mailto:` and validated fragment refs; image refs map through a documented author-friendly media base into validated Entity assets. Unsafe schemes (`javascript:` etc), ambiguous target, unapproved remote image load or arbitrary server-side fetch fail. Intentionally authored direct links to known unlisted URLs may be allowed under classified safe-link rules but no auto-discovery; changing a source path never changes EFS identity. Modules must access resources only through approved application ports; external provider retrieval requires separate permission and bounded adapter.

**SPECIFICATION GATE:** Final locators/namespace literals, portable allowed Unicode/filename grammar, symlink/mount/hardlink ambiguity profile, case-insensitive filesystem collision policy, link base semantics, fragment ID policy, allowed external schemes/hosts and trusted media reference grammar are not closed. Implementations may not invent answers.

### D12 — Integrated validation, module compatibility and migration

**ACCEPTED:** Use one versioned core manifest schema and governed versioned subordinate contracts for content structure, property definitions, graphic roles and advanced JSON modules. One coordinating validation process enforces structural syntax plus all graph, source, routing, ancestry, exposure, media and capability rules. Registered extensions do not become separate publication authorities; no arbitrary code loading. Module declaration names a registered module and supplies typed values; module contract records stable name, version, typed inputs/defaults/bounds, permitted output/capabilities, application port needs, accessibility/safety restrictions, and platform compatibility. Domain and application contracts stay independent of framework/providers under mandatory Hexagonal Architecture. Unknown module, incompatible version, undeclared field or unsupported schema fails closed with actionable safe diagnostic. Adding an optional compatible module must not change unrelated installations; changes to supported module versions require explicit compatibility proof. Breaking schema/module changes require new major contract version and explicit reviewed migration, no hidden rewrite of IDs, routes, properties or source claims. Independent manifest schema, JSON-content schema, module-contract and Solo product-release version identities do not silently collapse; registry revisions also governed. Validate whole published graph including unlisted, with one selected source per representation, safe media and public projection before new candidate activation; no partial publish on error. A previously validated deployment may remain serving if a new candidate is rejected under later deployment policy. No claim of successful publish until complete proof.

**MANDATORY VALIDATION GROUPS:** (1) strict UTF-8 JSON and supported schema; (2) one valid published EFS ownership graph; (3) explicit and collision-free JSON/Markdown source candidates and one selected safe source; (4) safe validated body and registered modules; (5) additive property cascade, locations, graphics and public-only projection; (6) locale, base, alias and all route collision checks; (7) safe public assets, links, metadata and discovery; (8) atomic all-or-nothing candidate disposition. Diagnostics identify EFS/field and reason, not sensitive paths. The exact ordering can be optimized only while preserving full coverage.

**SPECIFICATION GATE:** Exact registry/manifest version matching, pinned dependencies, installation/module lifecycle, semantic-version ranges, format assertion mode, exact diagnostic shape and migration command/interface remain to be made normative before application code. Do not label examples such as `1.0.0` or `media.carousel@1.2.0` as shipped modules.
