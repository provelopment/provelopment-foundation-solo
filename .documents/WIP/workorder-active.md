### 3. Required behavior and proof — R02.A

1. **Positive graph construction.** Build a valid minimal single-Entity graph and a valid expanded graph with multiple Facets and multiple Sites/Pages. Every valid Facet has at least one Site, every valid Site at least one Page, and every valid published Page at least one representation. The model must never manufacture the starter `main` / `main` / `home` structure by guessing; that **seed** belongs to `R02.C`. Existing `EntityIdV1` is reused or delegated to for the identical accepted identity grammar rather than reimplemented inconsistently.
2. **Exactly one Entity, immutable scoped identity.** The graph root cannot contain a second Entity, and no public constructor or mutation path admits it. Validate all four identity levels without repair, case-folding, slugification or inference. Test empty, non-ASCII, uppercase, illegal punctuation, leading/trailing or doubled hyphen, overlong ID and boundary-valid 63-byte ID. IDs remain identical after changing merely associated display labels or externally supplied address/locale/context fixtures; no locale, hostname, public route or geographic fact becomes an identity source.
3. **Parent-scoped uniqueness.** Reject two Facets with the same ID in one Entity, two Sites with the same ID in one Facet and two Pages with the same ID in one Site. Positively accept identical Site/Page tokens under **different** legitimate parents and the same token at different levels. Avoid a global uniqueness table that would incorrectly reject these.
4. **Direct parentage and refusal.** Every child belongs to exactly the direct nested owner that contains it. No orphan, parentless entry, invalid cross-parent association, second Entity, duplicate ownership or ambiguous short-ID lookup is accepted as a valid *published structural graph*. A qualified lookup/target needs the complete `Entity/Facet/Site/Page` lineage, checks all four IDs and refuses unknown/mismatched ancestors and wrong-site/wrong-facet hits; a representation lookup also checks its canonical locale key. Preserve errors as typed, safe, stable diagnostic categories without echoing secrets or making a first-match choice.
5. **Representation identity and limits.** One or more representation membership entries per published Page; duplicate **canonical** locale keys for the same Page refuse, while the same key under different Pages is legitimate. A locale is not a Page ID, location or route segment. Do not accept raw uncanonicalized authored locale input as a validated publishable representation; the real BCP47/Unicode 18 validator and its future proof belong to subsequent scope. Do not infer publication from filenames, draft entries or a claimed source file. Respect the architectural EFS structural bounds where applicable (no more than 10,000 EFS nodes including representations, 500 Pages or 100 representations per Page), with deterministic rejection and no partial accepted result.
6. **Immutable, valid output.** Constructors/builders return a complete valid graph or typed refusal, never a partially valid public graph, silent truncation, auto-repair, implicit reparenting or mutable escape hatch that invalidates checked cardinality. Read-only traversal must preserve authored child order while uniqueness/refusal remain order-independent. No public constructor may turn an unvalidated draft into a published graph. Include adversarial order permutations and safe diagnostics. Avoid speculative public serialization schema, dependency selection or future migration format.
7. **Nonregression and A1.** `solo-domain` remains `std`-only with **zero** dependencies. All existing CLI/application/adapter smoke, architecture graph/source/refusal fixture, test-tripwire, security scans and release checks must continue to pass on the exact source revision. The new implementation introduces no HTTP/browser or product publication behavior and no unsupported unsafe or provider import. Browser, contact form, accessibility and released-product checks are `NOT APPLICABLE` for this pure-domain scope; do not present them as passed.

**Design latitude:** Choose the smallest understandable pure-Rust structs/enums, validation functions and focused tests fitting these exact accepted contracts. Do not add a generic graph framework, persistence abstraction, second authoritative registry, unnecessary wrappers or a future-guessing API. If the requirements cannot be met without an unapproved Unicode parser, new crate or broader schema decision, record the precise blocker and STOP instead of implementing a misleading weaker substitute.
