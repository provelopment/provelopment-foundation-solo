## 2. Exact R00.A identity and publication decisions to record

### A. Identity syntax, scope and stability

1. **Separate identity from labels and addresses.** Each Entity, Facet, Site and Page has an explicitly persisted technical ID. ID strings do not encode or derive from display name, slug, public route, domain, locale, physical location, filesystem path or provider account. A localized representation is uniquely identified **within its Page** by its explicitly authored, canonical full region-qualified BCP 47 locale tag, under the already-approved locale contract; it is not a second Page ID.
2. **Technical ID grammar.** For the four EFS identity-bearing levels only, use canonical lowercase ASCII tokens matching `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, with a maximum of **63 ASCII characters**. No leading/trailing hyphen, consecutive hyphens, whitespace, underscores, uppercase aliases, non-ASCII characters, slash, dot, percent escape or silent case-fold normalization. Reject invalid authored IDs with a specific diagnostic; do not repair or derive them. The token grammar is for IDs **only**, not a rule for public Page-route tokens, which retain their separately accepted public/unlisted casing behavior.
3. **Uniqueness scope.** Exactly one Entity ID per Installation; Facet IDs unique within that Entity; Site IDs unique within their **own Facet**; Page IDs unique within their **own Site**. Reuse of `main` or `home` under different valid parents is allowed because the ownership context differs. Within each scope, duplicate authored canonical IDs are invalid. This order establishes no ID-alias mechanism; any future identity aliasing requires separate Owner acceptance and must not create ambiguous identity claims. Different levels may legitimately use the same token. Do not introduce a cross-Installation registry, tenant ID, Spoke or global uniqueness service.
4. **Durable reference.** Authoring/publication declarations persist the IDs and explicit parent ownership. Changing labels, public addresses, localized representation sets, base URL or EFS properties never mints a replacement ID. An intentional parent move, identity change or deletion is an explicit, later-approved migration with reference checks; no filename move, route change or implicit inference silently reparents or recreates a node. The format of references and migration tooling remains open.

### B. Minimum default model and cardinality

5. **Initial establishment.** The author explicitly supplies the one Entity ID; Solo does not guess it from a name or hostname. A new usable Installation is seeded with exactly one default Facet of ID `main` and display label `Main`, and exactly one child Site of ID `main` and display label `Main Site`. Identical IDs are valid here because the scopes differ. These are initial authoring defaults, **not** reserved words, required route segments, geographic labels or new ownership levels. Labels are editable without an identity change.
6. **Starter Page.** The initial default Site includes a Page with ID `home` and display label `Home`, with at least one real authored localized representation for a supported **explicitly selected full locale**. No locale is inferred or hardcoded by this package; the exact Site/default-locale configuration and public Home routing remain R00.B. The starter Page is a usable authored Page, not an automatically published undeclared source file or an empty placeholder. Further starter Pages are not mandated here. Additional Facets/Sites/Pages are explicit authoring actions and must meet the published-cardinality rules.
7. **Published view cardinality.** Exactly one Entity; at least one Facet per Entity; at least one Site per published Facet; at least one Page per published Site; at least one valid localized representation per published Page. Each child has exactly one declared direct parent; no cross-parent borrowing or silent sibling fallback. For this rule, the published graph includes validated, directly reachable **unlisted** representations as well as public representations; visibility controls discovery, not whether an admitted representation belongs to the graph. A partially authored structure may exist only as a non-published draft under C, not as an exception to the published model.

### C. Draft and publication authority

8. **Incomplete drafts are allowed outside the published graph only.** Authors may retain incomplete content or work-in-progress declarations outside the authoritative published set. Such drafts do not count toward published cardinality, have no public route/discovery rights, and cannot be implicitly promoted by file presence, directory scans or a label such as `draft`. Explicit admission to the published set requires a complete, valid declaration and the same validation as any other published item. Exact storage locations and draft metadata format remain R00.D.
9. **One authoritative publication manifest.** A single explicit, versioned publication declaration is the sole authority for the one Entity and the published EFS ownership graph, including stable IDs, direct-parent associations, the published Page set, supported locale representations, and explicit source references. Only explicitly admitted complete entries publish; a file, property or route declaration alone does not. Logical semantics are approved here; physical file format, field names, locator syntax, content-section schema and manifest schema version number remain for R00.D and adjacent contracts.
10. **Source integrity.** Every published localized representation explicitly binds to an authored content-source reference belonging to its declared Page. That reference must resolve to exactly one existing, valid and permitted authored source, within the eventual validated source boundary; no implicit path matching, first-file-wins, search-order fallback or sibling source substitution. Two distinct published representation claims must not silently claim the same authored representation source; any intended sharing or generated content requires its own later explicit contract. Undeclared files are non-publishing; declared missing/unsafe/ambiguous sources fail validation. Generated output and public assets never become the authored manifest authority.
11. **Fail-closed validation contract.** Reject with actionable diagnostics: a second Entity; missing/invalid IDs; duplicate IDs in the relevant parent scope; missing, unknown or ambiguous parent; orphan Site/Page/representation; illegal cross-parent binding; empty published Facet/Site/Page; missing published representation; duplicate locale within one Page after canonical locale normalization; undeclared content publication; absent, duplicate-claimed, unsafe or ambiguous authored source references; and undeclared publication inferred from a directory or filename. Do not hide errors by inventing a default parent, picking the first match, reassigning identity or redirecting to a sibling. Each diagnostic must identify the affected declaration/ID and why validation failed, without exposing server-private paths or secrets.
