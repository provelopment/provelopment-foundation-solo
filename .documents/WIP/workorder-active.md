#### 3B. Contact request contract, concrete bounds, and normalization

- Exactly **three visitor input fields**: `name`, `email`, `message` (in addition to non-personal, server-issued CSRF/idempotency control tokens). No extra data-field, prechecked consent, attachments or tracking fields.
- Ratified maximums: `name` **1–100 Unicode scalars after NFC and edge trim**; `email` one §6.2J.9 addr-spec with **≤254 UTF-8 octets** after trim (do not lowercase or rewrite the local part); `message` **1–4,000 Unicode scalars after NFC**, with CRLF normalized to LF before scalar count. Allow ordinary LF/TAB within message; reject other ASCII controls, NUL, header injection and unsafe encoding. Name rejects all control characters and line breaks. Preserve typed input semantics and never interpret as markup.
- Maximum **16 KiB raw HTTP request body before parsing**, and **16 KiB decoded UTF-8 payload** after structural decoding; both ceilings enforced, so encoding expansion cannot evade the limit. Reject additional, duplicate or unknown visitor fields, malformed body, invalid UTF-8, wrong types, empty fields, unsafe headers and oversize without partial acceptance or truncation. Transport-created security tokens belong to a separate closed envelope, not the three-field `ValidatedInquiry` payload. Validation is server-authoritative.
- Where the input contract is JSON or `application/x-www-form-urlencoded`, define strict decoding and repeated-key refusal; do not silently add an unbounded parser or accept unsupported media types. Message text is inert on all output paths.

#### 3C. Clear application vs delivery outcomes; safe operation

- Keep the **seven exact application outcomes** in §6B.5. `invalid_request`, `not_configured` and `rate_limited` are produced by the inbound/application boundary, **never** by `ContactDelivery`. `ContactDelivery` returns only the four typed transport outcomes `accepted_for_delivery`, `rejected_downstream`, `temporarily_unavailable`, `indeterminate`. The application maps these into the seven-outcome visitor model. Invalid CSRF/origin maps to `invalid_request` with a generic form-level security refusal, **not** a fictitious field error. No provider error text or client-supplied status is trusted.
- `accepted_for_delivery` proves only that the real delivery adapter has an externally evidenced provider/transport acceptance, **not** final inbox receipt. Fake/no-provider/log-only paths cannot return it. No adapter configured or no private recipient = disabled/unavailable, never accept-and-drop. `mailto:` is a **separate** client-mail action backed only by intentionally public `contact.email`.
- Idempotency: a server-issued opaque attempt token is carried as an ordinary form control and bound to validated server-side state; the same token may authorize **at most one outbound dispatch** even under concurrent, duplicate or multi-instance requests. Maintain only a short-lived **non-content deduplication record** (token hash, state, timestamps, nonreversible request digest), with a **24-hour lifetime**; it is operational adapter state, **not contact-message retention**. Never cache a message body or address there. If durable/atomic deduplication across applicable instances is unavailable, the form is disabled instead of making an unverifiable exactly-once promise.
- No blind retry after `indeterminate`. A retried attempt with the same token returns its last safely known result or `indeterminate` **without dispatching again**. A new attempt is permitted only after a clear, new visitor action with a freshly issued token and a warning about possible duplicates; any automated resend with an indeterminate first outcome is prohibited. Do not guarantee downstream exactly-once receipt if the provider cannot prove it.

#### 3D. Abuse control and privacy defaults (first-release policy)

- Server-side first-party rate control, applied **before delivery**: default **3 attempted submissions per verified client network peer in a rolling 15-minute interval** and **60 attempted submissions per Installation in a rolling one-hour interval**, counting accepted and refused form attempts after they reach the bounded request entrypoint. Exceeding either yields `rate_limited` and no outbound action. Authored Page/locale/route/IP headers cannot grant a higher allowance. Thresholds are first-release defaults, not worldwide security guarantees; Owner-controlled future tuning requires its own accepted operational configuration boundary.
- An IP/client-peer used as an abuse key comes from the actual trusted transport/proxy configuration, **never** raw `X-Forwarded-*`, `Host`, `Origin` or geolocation as authority. If a deployment cannot identify a trustworthy peer or consistently enforce bounds across active instances, the module remains unavailable (`temporarily_unavailable` or `not_configured`, as appropriate); no silently weakened limiter, tracking identifier, third-party CAPTCHA or account system.
- Solo core does **not** persist name, email, message or request bodies. Operational limiter/dedup keys expire with their configured windows (max 24 hours for the default attempt record); ordinary logs contain no message, email, address, secret or provider body. Credentials, internal recipient and delivery mapping are private configuration; one private recipient per Installation in first release. Provider retention, applicable privacy/legal notice and deletion terms are **separate mandatory provider-adoption prerequisites** before activating a real delivery provider, not false promises or invented universal retention-law compliance.
- `notice` presents a clear public privacy-information link for the module. **No consent checkbox or acknowledgement** is included in the first release: consent/authorization claims are not guessed and a future legally required change is a separately approved amendment. No analytics by default; any analytics provider requires a separate Owner order and cannot collect form content or become a publication prerequisite.
