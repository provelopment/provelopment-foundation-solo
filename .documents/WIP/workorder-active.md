### 2. Required A1 Contract — durable, practical and strict

In the Architect SOP §7B, make the following binding, without contradicting existing §7B(e1):

1. **Freshness is a tested quality attribute.** Before a new component is selected, before a version-changing code-bearing order is accepted, and in the regular maintenance review, determine the **currently published exact stable version**, vendor support status, EOL/deprecation status, release notes/security advisories, provenance and compatibility for every *relevant* component, including direct/transitive normal/build/dev/test dependencies; compiler/Cargo/rustup and std; `cargo-deny` and its external binary/artifacts; GitHub Actions and Node runtime requirements; hosted runner labels/compatibility; and future Node/TypeScript/Vite/browser packages **only after actually installed**. Record source, query date, installed/selected version, candidate version and disposition. Distinguish an **architecture-selected but not installed** future pin from an installed dependency. Do not assume every selected historical pin is installed or latest.
2. **Version choice.** Default to the latest verified **stable** and supported compatible patch/minor/major, or the latest **suitable LTS** where a maintained LTS exists (e.g. Node). Do not prefer an experimental, prerelease or unsupported release merely because its number is higher. Rust follows rolling stable without a distinct LTS; do not invent one. Never choose an older unsupported version for convenience or suppress a version warning. Compatibility with the accepted design, supported runner, exact contract and supply-chain provenance must be demonstrated before promotion. Unknowns are `UNVERIFIED` with an actionable decision, never silently treated as current.
3. **Warning standard.** Zero **unresolved actionable** version/deprecation/unsupported-runtime/EOL notices in actual GitHub Actions logs, check annotations and update alerts at acceptance. Record genuine warnings, including platform-managed ones, with source, affected version, support deadline, impact and a bounded remediation. No muted warnings, disabled checks, pinned deprecated actions, blanket ignores or misleading clean claims. A green status alone does not prove a warning-free run. If immediate safe remediation is impossible, the Architect returns `REVISE`/`STOP` for a material warning or seeks an **explicit, time-bounded Owner disposition** for lesser risk, never quietly waves it through. This is a strict maintenance objective, **not an impossible promise that GitHub can never emit a new warning**.
4. **Reproducibility versus currency.** Every verified update is locked to an **exact version, immutable commit SHA or verified digest** as appropriate. Never put floating `latest` into release/build instructions to appear current. Re-verify LTS, status, integrity and compatibility at the time of each update rather than blindly bumping pins. The architecture's fixed **product wire/content/schema/module contract versions** remain distinct from third-party dependency versions and are not opportunistically advanced.
5. **Upgrade lifecycle.** Discover candidates → classify urgency, affected environment and dependency graph → review vendor breaking changes, advisories, licenses, provenance and runner compatibility → propose smallest coherent Owner-authorized work order/PR (no silent `latest`) → change manifest, lock, toolchain and immutable action/binary pins *only in that approved scope* → run complete two-host offline-application and live advisory/security, architecture, negative/refusal, tests, reproducibility and future browser evidence where applicable → compare against baseline at source and final published HEAD → independent Architect `ACCEPT/REVISE/STOP` → separate Owner approval for merge/release/deploy. Have a concrete recovery path using the previous verified commit/lock/artifact; do not authorize destructive Git or undeclared rollback. Fail closed on provenance or incompatible upgrades.
6. **Cadence and ownership.** GitHub Dependabot reviews installed Cargo and Actions weekly and proposes PRs only. The Implementation Agent, under an Owner-issued scope, checks exact component currency, runtime-support and warnings when touching versions. The Architect independently verifies at code-bearing acceptance. An Owner-visible **weekly review** of pending Dependabot proposals plus manual toolchain/rustup, hosted runners, external scanner binaries, license notices and future installed ecosystems is part of the permanent maintenance process; urgent critical/high or malicious advisories are triaged immediately through the existing security gate, independently of the weekly cadence. Open proposals are not proof an upgrade passed tests. Record deferred updates and explicit review dates in the canonical run report rather than adding a new register or WIP file.

**Operational text** in Implementation SOP must explain how to create the concise version ledger, review Dependabot PRs, check relevant GitHub warnings and vendor release sources, carry out an authorized bounded update, retain pinned artifacts, prove backwards behavior and restore safely. `AGENTS.md` links to the **one** authoritative SOP; Architecture's §6A.2 should not become an independent, contradictory policy. Preserve the established project support/LTS **product-release** policy in §6C; it is separate from build-tool LTS selection.
