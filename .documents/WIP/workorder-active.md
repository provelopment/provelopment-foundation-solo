### 1. Owner decision, objective, and non-negotiable result

The Owner approved a **hybrid platform-specific security correction** instead of either unmodified alternative in R04's final STOP report. The approval has two distinct parts:

1. **Linux:** eliminate the disposable named staging namespace entirely. Securely adopt the caller-selected root without following intermediate symlinks/magic links; retain its trusted descriptor; create all staged shards directly in that descriptor with the **already-pinned safe `rustix` `O_TMPFILE | O_EXCL` operation**. No staging directory or shard pathname is created or removed by this transaction. Kernel handle closure owns the lifetime. No new Linux unsafe, FFI, crate or feature.
2. **Windows:** preserve the successful staging object's no-writable-alias/nameless-after-creation security model. Authorize **only narrowly isolated native Windows operations** in the existing audited `crates/solo-adapters/src/source_read_native.rs` boundary to (a) traverse/adopt the selected root one component at a time with no reparse following, (b) create the task-owned namespace and temporary shards **relative to verified retained parent directory handles** using the already-imported `NtCreateFile` entry point in a narrowly new `FILE_CREATE` call form, and (c) mark/remove the **exact held owned handle**, not a looked-up pathname, with an appropriately scoped `FileDispositionInformationEx` operation. The new by-handle disposition call and its unavoidable, minimal Windows-only `unsafe` are expressly permitted **for this order only**. Prove their exact host semantics before relying on them. Use `FILE_DELETE_ON_CLOSE` for shards when host-proven necessary to prevent orphaned accessible plaintext on abrupt process death; this is not permission to leave visible, readable or writable staged objects.

**Success condition:** eliminate the independently confirmed F2 root/adoption/creation redirection and F5 unowned-object deletion races on **both** Ubuntu 24.04 and Windows 2025 while retaining the accepted R03/R04 one-selected-body-at-a-time, disk-backed source-stage design, true all-or-refused candidate construction, sealed and bounded member reads, and existing registered diagnostics. **No security contract is narrowed**: in particular, Windows may have a transient create-name only during an atomic protected create→by-handle detach, never an accepted shard that remains reachable by name; no unauthorized writable/readable alias; no partial/foreign deletion; no pathname lookup as cleanup authority.

The platform mechanisms above are **Owner-selected design directions, not presupposed proven API behavior**. First verify the actual exported pinned bindings, access rights, share flags, rename/delete-pending behavior, filesystem support, handle lifetimes, and Windows 2025 cleanup semantics in safe, owned disposable experiments. If a necessary claim cannot be proven inside this exact ledger/authority, **STOP**, retain the previous green code rather than implement a weaker substitute, and report the precise missing operation or permission. No speculative fallback to a visible Windows shard, non-atomic pathname deletion, weakened F1, or extra native privileges.

### 5. Implementation, lifetime and failure handling

1. **Linux:** remove the named `solo-source-stage-*` namespace and its cleanup calls from Linux compilation paths entirely; retain the trusted staged root descriptor for the store's lifetime; open unnamed shards directly there. The caller-owned root is never deleted or chmod-modified, and unrelated root entries/sentinels are untouched. Preserve shard grouping and the 64 MiB target, per-member range validation, sequential disk staging, fallible bounded reads and finalization. Refuse if the held target no longer qualifies as an acceptable directory. No new public authority.
2. **Windows:** retain independent trusted root and namespace handles; relative-create each owned namespace and shard; detach the shard **by its held handle** before any staged member becomes accessible, including on error paths. Protect the transient named interval through file-sharing/handle flags, prevent a second writable alias, and close/destroy safely on every early return. Delete the namespace, if truly owned, by held handle after all shard handles are closed; never delete an unowned empty directory. Nonempty owned namespace, permission failure, cancellation, and OS-not-supported cases must remain failures/limitations, not silent destructive cleanup. Do not suppress an outstanding cleanup failure by ignoring the result if doing so would make candidate success unjustified.
3. **Failures:** preserve the actual production-path injection seam and registered refusal vocabulary. Test write and short-write after one or more successful members, real permission denial where executable, injected capacity/quota, flush/finalize, hostile root and namespace replacement, failure to detach/mark-for-delete, and owner-versus-adversary cleanup. No returned candidate or earlier staged bytes accessible upon a refused transaction. If cleanup can fail after a candidate would otherwise succeed, require it to be handled before success is exposed, with a documented, testable lifecycle. Never turn unsafe-path/IO refusal into a missing JSON body or Markdown fallback. No source reader reopens previously selected authored files.
4. **Test migration:** Linux tests formerly inspecting the disposable `solo-source-stage-*` namespace must be updated to assert the **stronger zero-created-entry property at the caller-owned root**. Preserve or strengthen every hostile-substitution, original-source and cleanup assertion; rename platform-specific tests transparently in the report. Do not delete a failing adversary merely because the redesigned Linux store no longer has a named namespace. Windows keeps its native namespace-specific negatives.
5. **Crash/lifetime:** distinguish `Drop`/unwind from process termination. When safely testable, spawn a bounded child that stages synthetic data and is terminated, then assert only owned data has vanished or quantify the exact leftover risk. No disk-fill, unbounded allocation or dangerous OS configuration. A process termination is not evidence of an atomic source-set snapshot.
6. **Documentation:** update affected inline technical comments accurately (Linux no namespace, Windows native exception, OS host limits, lifetime, deletion semantics).
