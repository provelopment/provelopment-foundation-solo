## 4. Mandatory R03.B implementation contract

### 4A. The one location fact and inherited-target identity

- Continue to use the single registered `location` property on the five EFS levels, never a `Facet`/`Site` type or routing key. A fact is independently authored by `add`, with stable `(originOwner, factId)`, `kind` (`association` / `premises`), closed `LocationFieldsV1` and whole-record `public`/`internal` exposure. `extend` is an operation and **not** a new effective value, independent fact or background merge.
- To extend at current `owner`, require `request.target_owner().is_ancestor_of(owner) == true` (strict complete qualified **direct-chain** ancestor, never current node/sibling/other Entity). Require exactly one effective **parent-inherited** location fact whose **original** owner equals `target.owner` and whose original fact ID equals `target.factId`, and whose identity is still present after local inheritance selection. Never match only by fact ID, geographic name, Page ID, locale, current field origin or a Site name. If two inherited facts from distinct original owners share a `factId`, the qualified target must select exactly one without ambiguity or cross-update.
- An Entity-root `extend` refuses; a current-node target refuses; a sibling, cross-Facet, cross-Site, cross-Entity, child/descendant or wrong-locale target refuses; a fact missing from the immediately inherited effective set refuses; a formerly inherited fact dropped by an intervening `suppress` refuses; a fact suppressed **at this node** cannot be extended, even when named by a valid ancestor. Do not fall back to an ancestor after suppression or mutate a different identity with a similar label. A same-node newly `add`ed fact is not eligible for `extend` in that same declaration.
- Preserve R03.A `add` uniqueness by `(current authored owner, factId)`, inherited fact uniqueness by `(original owner, factId)`, effective 0–16 location facts, and entire one-Entity parent-first failure closure, even when the invalid declaration belongs to an unrelated or **unlisted** representation.

### 4B. Typed overlay, authored operation order and provenance

- Resolve the immediate parent's effective location collection first. For a local `inherit` declaration, carry the parent's resolved facts and events, then process every local `currentContext` operation **in its array order**. For local `suppress`, clear inherited facts, record suppression, then process local additions in authored order (but no extension of a suppressed ancestor). The literal `"none"` makes no local contribution and does not mean absence. No nearest-wins or hierarchy search.
- On valid `extend`, update the **existing fact's** typed fields in place by overlaying **only** members explicitly in `set`; overwrite existing members or add newly set members, preserve every untouched member, keep all ten allowed field names closed, and treat `coordinates` as one validated atomic field. No deletion, `null`, arbitrary fields, default values, inferred geography or side-effect. Preserve `factId`, `kind`, `originOwner`, `originLocalIndex`, whole-record `exposure`, effective list position and stable independent fact count. An extension cannot elevate `internal` to `public`, even if a typed wrapper claims `Exposure::Public`.
- The sole `fieldOrigins` record for a resolved location fact must contain **exactly** each currently set field and no extras, with `{owner, localIndex}` from the last **explicit** local `add` or `extend` operation to set it. An `add` sets each initial field origin to its own qualified owner and its own zero-based local operation index. An extension changes only the origins of fields named in `set`, to the extending qualified owner and the extension's zero-based local array index; untouched field origins persist through every descendant and repeat extension. No `operation` member in a field origin, no second provenance model, no original-owner/index rewrite.
- Keep the single ordered `resolutionEvents` record: inherited event when an explicit declaration actually carries inherited values (per existing R03.A behavior), `suppressed` when suppressed, `added` for each independently authored `add`, and **`extended`** for each successful extension, with current owner, exact local index and the extension's `targetFactId`. Record events in actual ancestor then local order, including mixed `add/extend` interleaving. An `extend` does **not** also emit an `added` event, append an extra fact, or turn into an `inherit` fallback.
- Maintain one straightforward, deterministic, parent-state-reuse implementation; avoid rebuilding independent ownership graphs or scanning unbounded ancestors for each fact. `LocationFieldsV1`'s private validated members should remain validated; prefer one bounded typed overlay method instead of round-tripping through JSON/string maps or duplicating a parallel location type.

### 4C. Closed syntax, typed entry safety, refusals and diagnostics

- Preserve the existing strict authored syntax: closed `extend` `{operation,target,set}`; closed `target` `{owner,factId}`; fully qualified contiguous owner with validated technical IDs and **canonical region-qualified** representation locale; nonempty closed `set` using exactly the ten validated `LocationFields` members, with the same scalar/geometry/country-code checks as `add`; **no** authored `exposure` in an extension. Preserve all existing invalid syntax tests, including empty/missing `set`, invalid WGS84 coordinates, invalid country-code form, extra members, wrong types/locale/lineage and invalid fact ID.
- **Close typed-API bypasses:** `LocationExtensionRequestV1::new` is public and can receive `LocationFieldsV1::new()`; `AuthoredPropertyValueV1::new` is public and can pair an extension with `Exposure::Public` even though authored extension exposure is forbidden. At the domain's validated declaration boundary, reject an empty extension `set` and reject a public extension wrapper (or use a minimally revised typed encoding that cannot express these states). The adapter's existing internal placeholder must remain non-semantic and **never** replace or elevate inherited exposure. Test both direct typed and real-JSON entry points. If choosing a minimally revised encoding, preserve the accepted JSON contract and author-facing API and report exactly how the bypass is closed.
- Distinguish runtime invalid extension **by typed cause** (at minimum forbidden target lineage, missing/not-currently-inherited target, suppressed target, and repeated same-node target). Recognize that two `extend` requests to the same `(originOwner, factId)` at one node are a **conflict/refusal**, not last-one-wins or idempotent deduplication, whether they set the same or different fields. Use canonical engineering code **`LOCATION_INVALID_EXTEND`** for these invalid-operation outcomes as mandated by Architecture §6.2K.4; do **not** return the obsolete `LOCATION_EXTENSION_NOT_IMPLEMENTED_IN_R03A` code for valid R03.B extension execution. Do not create unregistered new public engineering codes; stable typed detail tokens may distinguish causes without carrying authored values. Malformed JSON envelope/fields remain closed typed **declaration** refusals.
- Diagnostics should identify the **actual offending qualified owner and the registered `location` key** where available, rather than falsely labelling an unrelated requested target as the culprit. Keep every diagnostic safe: only approved structural identifiers, registered keys, code/category and bounded non-sensitive wording, never the raw location fields, an internal value, mailbox, filesystem path, token or authored secret. A refusal anywhere must prevent `ManifestPropertyCandidateV1`/`PropertyResolutionCandidateV1` creation and public projection of any partial result.
- Preserve the identity and semantics of the other eight registered keys and their existing cardinality, exposure and suppression rules, and preserve `propertyRegistryVersion = "1.0.0"`, because this completes semantics **already governed by that accepted version** rather than registering a new key or format. Repair code comments and historical R03.A tests/API descriptions that would become false when extension is actually supported. Do not weaken or remove unrelated coverage to make tests green.

### 4D. Safe output and non-publication

- Only **validated `public` whole location facts** appear in the separate public property projection, with their correctly overlaid **data** but without internal `fieldOrigins`, `originOwner`, `originLocalIndex`, resolution events or raw extension requests. An inherited `internal` fact remains wholly absent after a public-looking `set` even if a descendant also has an independently authored public fact. Suppression stays final and no public fallback resurrects a cleared or filtered value.
- `validate_manifest_property_candidate_v1` must still start from actual `ParsedManifestCandidateV1`, translate *all* five-level owners including those without any `properties`, match that complete inventory against `EfsOwnershipGraph`, and resolve **all** owners before returning a requested target.
